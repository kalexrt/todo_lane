# ADR 0002 — Add SQLite persistence for tickets and projects
**Status:** Accepted
**Context:** The tracker's constitution originally locked state to in-memory-only, resetting on every restart — a deliberate choice to keep the initial barebones demo minimal. That reset-on-restart behavior is no longer acceptable: data created in one run should survive the next. The CONSTITUTION's own hard rule ("never add persistence... without an ADR") requires this decision to be recorded before the change is made.
**Decision:** Add SQLite as the backend's only persistence mechanism, accessed through the existing `TicketsService`/`ProjectsService` seam (no new architectural layer, no ORM framework — keeps the "mid-level engineer onboards in under a week" bar). The services' public methods and return shapes stay the same; only their internal storage moves from an in-memory array to a SQLite-backed store. A single file-based database, created if absent, colocated with the backend package.
**Consequences:** State now survives process restarts, satisfying the enhancement's purpose. The backend gains one new runtime dependency (a SQLite driver) and a data directory that must exist and be writable. Test isolation now requires either an in-memory SQLite database or a fresh file per test run to keep the existing hermetic-test guarantee. `docs/context/PRODUCT.md` and `CONSTITUTION.md` are updated alongside this ADR to reflect the new stack fact (DB: SQLite) and drop the "no persistence" scope boundary.
